# Step 4: プロテクトモード → ロングモード (64-bit)

## 目的

ゲスト CPU を 32-bit プロテクトモードから 64-bit ロングモードに遷移させる。
**ページテーブル**、**CR3**、**CR4.PAE**、**EFER.LME** を導入し、ハードウェア仮想化の中核である2段階アドレス変換を明らかにする。

## 背景

### ロングモードの要件

この実装では、VMM が準備を行い、ゲストがプロテクトモード（CR0.PE=1、CR0.PG=0）から次の順序で遷移する:

1. **VMM** がゲストメモリにページテーブルを構築する
2. **VMM** が EFER.LME=1（MSR 0xC0000080 の bit 8）を初期設定する
3. **ゲスト** が CR3 にページテーブルの先頭アドレスを設定する
4. **ゲスト** が CR4.PAE=1 を設定する（ロングモードのページングに必要）
5. **ゲスト** が CR0.PG=1 にしてページングを有効化する
6. **ゲスト** が L=1、D=0 のコードセグメントへ far jump する

PAE と LME が設定された状態でページングを有効にすると、プロセッサはロングモードを起動する (EFER.LMA が内部的にセットされる)。ただし 64-bit 命令デコードはまだ始まらない — CPU は**互換モード** (32-bit コードを実行するロングモードのサブモード) にある。その後の **L=1** のコードセグメントへの far jump が真の 64-bit 命令実行を開始する。

### x86-64 ページテーブル階層

ロングモードは通常4段階の階層を使用する:

```
CR3 → PML4 → PDPT → PD → PT → 4KB ページ
```

このステップでは 2MB ページ (PD エントリの PS=1) を使ってウォークを早期終了するため、PT レベルはスキップされる:

```
CR3 → PML4 (Page Map Level 4)
        └→ PDPT (Page Directory Pointer Table)
              └→ PD (Page Directory)
                    └→ 2MB ページ (PS=1, ここで変換終了)
```

各エントリは 8 バイト。ページテーブルは 4 KiB 境界に配置し、2 MiB ページの先頭アドレスは 2 MiB 境界に揃える。このステップで使うフラグは以下の3つ:

| Bit | フラグ | 意味 |
|-----|--------|------|
| 0 | P | Present — エントリが有効 |
| 1 | RW | 書き込み可能 |
| 7 | PS | Page Size — 今回は PD エントリで1にし、2 MiB ページを指す |

### アイデンティティマッピング

ゲスト仮想アドレスとゲスト物理アドレスを同じ値で対応させることを、アイデンティティマッピングと呼ぶ。この実装では、ページングを有効にした直後も同じ位置のコードや GDT、far jump 用ポインタを参照できるように、低アドレス領域をそのまま対応づける。

```
仮想 0x000000–0x1FFFFF  →  物理 0x000000–0x1FFFFF  (最初の 2MB)
```

ゲストページテーブルは最初の2 MiB をマップするが、VMM が登録する RAM は1 MiB のまま。ページテーブルにマッピングを作るだけでは、対応するゲスト RAM は増えない。

### 2段階アドレス変換

EPT（Intel）/ NPT（AMD）を使う構成では、ゲストのページング有効化後、アドレスは次の2段階で対応づけられる:

```
ゲスト仮想アドレス
        │
        │  ゲストページテーブル (ゲストが構築, CR3)
        ▼
ゲスト物理アドレス
        │
        │  第2段階変換 (KVM が構築)
        ▼
ホスト物理アドレス
```

| | ゲストページテーブル | 第2段階 (EPT/NPT) |
|---|---|---|
| 構築者 | ゲストソフトウェア (OS, ブートローダー, またはゲスト代理の VMM) | KVM カーネルモジュール |
| 変換内容 | ゲスト仮想 → ゲスト物理 | ゲスト物理 → ホスト物理 |
| 格納場所 | ゲストメモリ (CR3 がルートを指す) | KVM が管理するホストメモリ |
| フォーマット | x86 ページテーブル | ハードウェア定義のネストページテーブル (EPT/NPT) |

ハードウェアが両方の変換を処理するため、通常のメモリアクセスごとに VMM へ戻る必要はない。変換結果は TLB（アドレス変換のキャッシュ）などに保持され、毎回ページテーブル全体をたどるわけではない。

この分離により、ゲストに見える物理アドレスと、実際に使うホストメモリを独立に管理できる。Step 5 ではゲスト物理アドレス空間に RAM を割り当てない領域を設け、MMIO デバイスとして扱う。

### なぜ VMM が EFER.LME を設定するか

EFER は MSR（モデル固有レジスタ）で、ゲスト側の `wrmsr` 命令でも設定できる。この実装ではゲストの遷移コードを短くするため、実行開始前に VMM が `KVM_SET_SREGS` で LME を初期設定する。

## 実行フロー

```
VMM (microkvm)                                  Guest
──────────────                                  ─────
ページテーブルを構築:
  0x70000: PML4[0] = 0x71003
  0x71000: PDPT[0] = 0x72003
  0x72000: PD[0]   = 0x00083
KVM_SET_SREGS: EFER.LME = 1
KVM_RUN
                                                [リアルモード]
                                                  'R' と改行を PIO 出力
                                                  lgdt, CR0.PE=1, far jump
                                                [プロテクトモード]
                                                  'P' と改行を PIO 出力
                                                  CR3 = 0x70000
                                                  CR4.PAE = 1
                                                  CR0.PG = 1 → 互換モード
                                                  far jump (CS=0x18, L=1)
                                                [ロングモード: 64-bit]
                                                  'L' と改行を PIO 出力
                                                  hlt
```

文字と改行はそれぞれ別の `out` で出力し、その都度 `KVM_RUN` を呼び直す。VMM は `KVM_EXIT_IO` を6回、`KVM_EXIT_HLT` を1回受け取る。制御レジスタ操作などに伴う KVM 内部の VM exit と、ユーザー空間への復帰は区別する。

## 実装

変更するファイルは `microkvm.c` と `guest.S`。`boot.c` / `boot.h`、`Makefile`、VMM の exit handler は Step 3 から変更しない。

### VMM: ページテーブル設定

```c
/* ページテーブルを GPA 0x70000 に配置 (GPA 0 のゲストコードより十分上) */
uint64_t *pml4 = (uint64_t *)((char *)mem + 0x70000);
uint64_t *pdpt = (uint64_t *)((char *)mem + 0x71000);
uint64_t *pd   = (uint64_t *)((char *)mem + 0x72000);

pml4[0] = 0x71000 | 0x3;   /* present + writable, PDPT を指す */
pdpt[0] = 0x72000 | 0x3;   /* present + writable, PD を指す */
pd[0]   = 0x0     | 0x83;  /* present + writable + PS (物理 0 の 2MB huge page) */
```

`0x3` は P + RW、`0x83` は P + RW + PS。PML4[0] と PDPT[0] は次のテーブルを指し、PD[0] は GPA 0 からの2 MiB ページを指す。残りのエントリは匿名 `mmap` のゼロ初期化により無効（P=0）のまま。

ここではゲスト側の実装を簡潔にするため、VMM が固定アドレスにページテーブルを用意する。ゲスト自身が同じ場所へ書き込んで構築することもでき、動的メモリアロケータは必須ではない。

### VMM: EFER.LME

```c
sregs.efer |= (1 << 8);   /* LME = Long Mode Enable */
ioctl(vcpufd, KVM_SET_SREGS, &sregs);
```

### ゲスト: 遷移シーケンス (プロテクトモード内)

```asm
    /* CR3 をページテーブルルートに設定 */
    mov $0x70000, %eax
    mov %eax, %cr3

    /* PAE を有効化 — ロングモードの前提条件 */
    mov %cr4, %eax
    or $0x20, %eax          /* bit 5 = PAE */
    mov %eax, %cr4

    /* ページングを有効化 → ロングモード起動 (EFER.LME は設定済み) */
    mov %cr0, %eax
    or $0x80000000, %eax    /* bit 31 = PG */
    mov %eax, %cr0

    /* 64-bit コードセグメントへの far jump (GDT[3], selector 0x18) */
    ljmpl *far_ptr
```

`CR0.PG = 1` の後、CPU はロングモード互換サブモード (まだ 32-bit コードを実行)。far jump で L=1 のディスクリプタを CS にロードすることで、CPU が 64-bit 命令デコードに切り替わる。

`far_ptr` は、32-bit オフセットと16-bit セレクタを並べた6バイトのデータ。`ljmpl *far_ptr` がこれを読み、GDT[3] のコードセグメントへ移る。

```asm
.align 4
far_ptr:
    .long long_mode      /* ジャンプ先のオフセット */
    .word 0x18           /* GDT[3] のセレクタ */
```

### ゲスト: 64-bit コード (手動エンコード)

この実装では、64-bit モードでも同じエンコーディングになる `mov al, imm8`、`out`、`hlt` を `.byte` で直接記述する。これは実装上の選択であり、`as --32` だから64-bit 命令を記述できないという制約ではない。GNU `as` には `.code64` で命令のエンコードを切り替える方法もある。

```asm
long_mode:
    .byte 0xB0, 'L'     /* mov al, 'L' */
    .byte 0xE6, 0x10    /* out 0x10, al */
    .byte 0xB0, '\n'    /* mov al, '\n' */
    .byte 0xE6, 0x10    /* out 0x10, al */
    .byte 0xF4          /* hlt */
```

### GDT: 64-bit コードセグメント

```asm
    .quad 0x00209A0000000000    /* GDT[3] (selector 0x18): 64-bit コード */
    .quad 0x0000920000000000    /* GDT[4] (selector 0x20): 64-bit データ */
```

GDT[3] のコードディスクリプタについて、Step 3 との主な違い:
- **L=1** — CPU にこれが 64-bit コードセグメントであることを伝える
- **D=0** — L=1 の場合に必要 (D と L は同時に 1 にできない)
- このコードセグメントの base と limit は64-bit モードでは無視される

GDT[4] も追加されているが、この step のゲストはセレクタ `0x20` をロードしない。DS/SS は Step 3 と同じ `0x10` のまま。

## 出力

```
$ ./microkvm
Loaded guest: 4136 bytes
Starting guest...
R
P
L
Guest halted.
```

3文字が全3つの CPU モードの成功実行を確認: リアル → プロテクト → ロング。

## 重要な知見

このステップでは、VMM がゲスト用ページテーブルと EFER.LME を準備し、ゲストがページングを有効にして64-bit コードへ移る。ゲスト仮想 → ゲスト物理の変換と、KVM が管理するゲスト物理 → ホスト物理の変換は別の役割を持つ。ゲスト側で2 MiB をマップしても、VMM が用意した1 MiB の RAM が増えるわけではない。

## このステップで学べること

| 概念 | ここでの現れ方 |
|------|--------------|
| ページテーブル | 2MB huge page による 3段階アイデンティティマップ (PT レベルはスキップ) |
| CR3 | PML4 を指す — ゲストアドレス変換のルート |
| CR4.PAE | ロングモードの前提条件 (64-bit ページテーブルエントリ) |
| EFER.LME + LMA | LME が意思を宣言; LMA は PG 設定時に有効化 |
| 互換モード | PG=1 後だが far jump 前 — まだ 32-bit 実行 |
| 2段階変換 | ゲスト仮想 → ゲスト物理と、ゲスト物理 → ホスト物理の分離 |
| アイデンティティマッピング | ページング有効化の前後で同じコード・データを参照する |
| Far jump (L=1) | 64-bit ディスクリプタで CS をリロードし 64-bit 実行を開始 |
